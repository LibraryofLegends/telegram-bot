# 1. Purpose

The Library Of Legends Documentation Standard (LLDS) defines the mandatory structure, quality requirements and lifecycle for every official project document.

No official documentation shall exist outside this specification.

---

# 2. Scope

LLDS applies to:

- Repository documentation
- Governance
- Standards
- Architecture
- ADRs
- Modules
- APIs
- Database
- Telegram
- Operations
- Releases
- Templates

---

# 3. Guiding Principles

LLDS follows:

- Documentation First
- Architecture First
- Consistency
- Traceability
- Scalability
- Maintainability
- Simplicity
- Reusability

---

# 4. Document Classification

Supported document classes include:

- Foundation
- Repository
- Governance
- Standard
- Architecture
- ADR
- Module
- Reference
- Operations
- Release

Each document shall belong to exactly one primary class.

---

# 5. Mandatory Document Structure

Every official document shall contain:

1. File Card
2. Metadata
3. Table of Contents
4. Purpose
5. Main Content
6. Definition of Ready
7. Definition of Done
8. References
9. Related Documents
10. Revision History
11. Change Log
12. Approval Block

---

# 6. Metadata Specification

Mandatory metadata fields:

- Project
- Codename
- Document ID
- Version
- Status
- Classification
- Package
- Author
- Created
- Last Updated

---

# 7. Versioning Rules

Document versions follow Semantic Versioning.

Examples:

1.0.0

1.1.0

2.0.0

Major versions indicate structural changes.

---

# 8. Document Identifier Rules

Every document receives one permanent identifier.

Identifiers:

- shall never change
- shall never be reused
- remain reserved after deletion

---

# 9. Naming Conventions

Documents shall:

- remain descriptive
- avoid ambiguity
- use approved project terminology

---

# 10. Cross-Reference Rules

Documents should reference:

- Document IDs
- Related specifications
- Architecture decisions
- Standards

Broken references shall be corrected before release.

---

# 11. Quality Requirements

Official documentation shall be:

- complete
- verifiable
- current
- internally consistent
- technically accurate
- grammatically correct

---

# 12. Review Process

Every Stable document shall undergo:

- technical review
- editorial review
- architecture review (where applicable)

---

# 13. Approval Workflow

Approval stages:

Draft

↓

Review

↓

Stable

↓

Deprecated

↓

Archived

---

# 14. Template Compliance

All templates shall comply with LLDS.

Templates shall not introduce mandatory sections conflicting with this specification.

---

# 15. LLDS Version Lifecycle

Changes to LLDS require:

- documented proposal
- impact assessment
- review
- approval
- version increment

---

# 16. Compliance Levels

Level A

Fully compliant

Level B

Minor deviations

Level C

Legacy

Non-compliant documents require remediation planning.
